## 1. Executive Summary

Bastyde is a native Rust desktop GUI framework built on AccessKit, and it genuinely binds a real, unconditional platform accessibility bridge (AT‑SPI on Linux, UIA on Windows, NSAccessibility on macOS) on every window, with broad, correct static Role/Name/Value coverage across its ~56-widget catalog. This is the load-bearing foundation any of the three regimes require, and it is real, not a stub. However, the audit surfaced a small number of severe, code-verified defects that sit squarely in the framework's own responsibility and will affect **every** app built on it unless individually patched by app authors: (1) a live, reproduced bug where `BindingLevel::Rebuild` — the binding level used by essentially every data-driven collection widget (ListView, TreeView, TableView, TreeTableView, Repeater, GridView, ComboBox, Calendar, DockingLayout, MenuBar) — never marks the accessibility tree dirty, so screen readers can be served a stale tree indefinitely after ordinary model mutations; (2) the shipped default IntUI theme itself fails WCAG contrast minimums for its primary/destructive Button text, its `text_secondary` token, its keyboard-focus indicator, and its selection tint; (3) determinate progress narration is structurally silent even when correctly role-tagged; and (4) several WCAG 2.1-only capabilities (Reflow at scale, Non-text Contrast, Text Spacing, Identify Input Purpose) are partially or fully absent as framework primitives.

**A material correction from the independent re-check that reshapes this report's priorities: the contrast blockers (G1–G3) are cheap to close.** They are not a design overhaul. Every failing pair traces to a single hardcoded hex value in exactly two functions (`ColorTokens::light_default()` / `dark_default()` in `crates/bastyde-tokens/src/theme.rs`), the resolution chain from token → role → widget paint is already centralized and correct, and the re-check computed concrete replacement hex values that clear the relevant AA floor with margin in minutes of engineering effort (see §5a). The one sub-item that is genuinely a design decision — the `surface_selected` pale-wash selection tint, which cannot reach the 3:1 non-text floor as a flat wash without abandoning the "subtle tint" aesthetic — is scoped separately and recommended to ship with a secondary non-color indicator (a thin accent-colored edge) rather than blocking the rest of the fix. Separately, the framework already fully plumbs `prefers_high_contrast` from the OS into `PaintContext` (`crates/bastyde-core/src/widget/paint_context.rs:49`) but **zero widgets consume it today** — building a dedicated high-contrast/low-vision theme variant on top of that dead signal is additive, low-effort relative to a greenfield feature, and directly serves EN 301 549 §11.7 and users who need contrast well beyond the AA floor. Both tracks are required and are **complementary, not alternatives**: WCAG 1.4.3/1.4.11 bind on the *default* theme regardless of whether an optional high-contrast variant ships (see §5a).

Framework-level conformance posture, per regime, for an app built with **unmodified stock Bastyde widgets and the default theme**:

- **EAA / EN 301 549 (→ WCAG 2.1 AA)**: **Partial conformance.** The full 2.1 AA criteria set applies (EAA covers all electronic products, EN 301 549 folds in 2.1), and several 2.1-only gaps (1.4.10 Reflow, 1.4.11 Non-text Contrast, 1.4.12 Text Spacing, 2.5.7/2.5.8) plus baseline 2.0 defects (1.4.3, 4.1.2) are live in the framework's own defaults. An app cannot claim conformance without the (now confirmed low-effort) theme tweak and the `BindingLevel::Rebuild` dirty-flag fix.
- **US Section 508 (Revised, WCAG 2.0 A/AA + Ch. 3 FPC)**: **Partial conformance, narrower gap surface than EAA.** Because 508 incorporates WCAG 2.0 (not 2.1) by reference, several of the above gaps (1.4.10, 1.4.11, 1.4.12, 2.5.7, 2.5.8) fall outside 508's literal SC scope — but the Functional Performance Criteria in Chapter 3 (302.7 limited manipulation, 302.8 limited reach/strength) can still surface the scene keyboard-drag gap and the 22px Compact icon button as findings. The 2.0-scoped defects (1.4.3 Contrast, 4.1.2 Name/Role/Value) remain live blockers, though both now have a confirmed cheap fix.
- **France RGAA 4.1 (→ WCAG 2.1 AA via EN 301 549 bridge for native software)**: **Partial conformance**, same criteria scope as EAA, with the added practical exposure that RGAA audits are conducted with real screen readers (NVDA/JAWS) — which will catch the framework's "attribute present but functionally inert" defects (determinate `ProgressBar` value never reaching AT) that a pure code review might undercount.

None of the three regimes can be satisfied by the framework alone — conformance obligations attach to the shipped **application**, not the toolkit — but the framework currently ships several default behaviors that actively work against conformance rather than being neutral, which is the central, actionable finding of this audit. The re-check's headline good news: closing the two Blocker-tier defects (the AT dirty-flag bug and the default-theme contrast failures) is now confirmed as a matter of hours, not a redesign.

## 2. Scope & Method

This audit assesses the **Bastyde framework** (crates/bastyde-core, bastyde-widgets, bastyde-tokens, bastyde-platform, bastyde-app, bastyde-scene, and related crates) at `/home/cyril/Devel/bastyde`, not any specific application built on it. Bastyde is a toolkit; most WCAG/EN 301 549 success criteria have a **framework-vs-author responsibility split**:

- **"The framework guarantees this"** — a mechanism runs automatically for any app using stock widgets (e.g., every `Button` gets `Role::Button` + a name from its label).
- **"An app author can achieve this if they use the API correctly"** — the primitive exists and is wired correctly, but requires the app author to call it (e.g., `.alt(...)` on `ImageWidget`, `.access_described_by(...)` for error association).
- **"Currently impossible or missing"** — no framework primitive exists at all (e.g., `Identify Input Purpose`, independent Text Spacing controls).

Every finding below reflects the outcome of an adversarial code-verification pass: each original claim was independently re-derived from the actual `.rs` source (not docs/CLAUDE.md, which are known to overstate/lag reality), several were confirmed via live reproduction (headless `WidgetTree` tests exercising `ListModel::push()` → `layout()` → `sync_accessibility()`, and a determinate-`ProgressBar` value-staleness repro run via `rtk proxy cargo test`), and WCAG contrast ratios were independently recomputed from the literal theme hex values using the framework's own `relative_luminance()` implementation (`crates/bastyde-tokens/src/color.rs:255-264`), confirmed to match the standard WCAG formula. A **second re-check pass** (documented inline via the "Remediation" column in §5 and expanded in §5a) went further: each gap's severity was re-derived from first principles, two findings from the original pass were downgraded/refuted on closer reading (Spinner's live-region wiring, and `Blur`'s reduced-motion handling), and every confirmed gap now carries an explicit remediation classification (trivial tweak / dedicated-theme-color / small code change / larger effort / upstream-blocked) plus an effort estimate. File:line citations throughout are drawn from these verified assessments.

**Standards basis:**
- **EAA (Directive 2019/882) → EN 301 549 v3.2.1 → WCAG 2.1 AA.** EN 301 549 clause 9 restates the full WCAG 2.1 A/AA success criteria for any ICT; clause 11 adds software-specific native-application clauses (11.5 AT interoperability, 11.7 user preferences, 11.8 authoring tools).
- **US Section 508 (2017 Revised, ICT Refresh) → WCAG 2.0 A/AA + Chapter 3 (302) Functional Performance Criteria.** Section 508 incorporates WCAG **2.0**, not 2.1, by reference — several 2.1-only criteria are legally out of the SC table but can resurface via the technology-neutral FPC.
- **France RGAA 4.1 → WCAG 2.1 AA**, bridged to EN 301 549 clause 9+11 for native (non-web) software since RGAA's own test methodology is web-authored and has no official native-app equivalent.

## 4. Regime-Specific Analysis

### 4.1 EAA (Directive 2019/882) / EN 301 549

**In scope:** the full WCAG 2.1 A+AA success-criteria table, restated through EN 301 549 clause 9, plus clause 11's native-software AT-interoperability, user-preference, and (n/a) authoring-tool provisions. EAA applies to the widest range of ICT products (not just public procurement), so there is no carve-out for 2.1-only criteria.

**Verdict: Partial.** The framework supplies genuine, substantial machinery (real AT bridge, broad role/name/value coverage, working focus/keyboard infrastructure) that an app **can** build EN 301 549 conformance on top of — but ships several **default** choices that actively violate specific SC:

**Blocking gaps unique to this regime (2.1-only, therefore invisible under 508's WCAG-2.0 lens):**
- **1.4.10 Reflow** — fixed uniform row height (`list_view.rs:81`, `DEFAULT_ITEM_HEIGHT = 32.0`) clips rather than reflows at 200% text scale, in the framework's own default/fastest path.
- **1.4.11 Non-text Contrast** — light-theme focus ring (2.47:1) and selection tint (1.19–1.41:1, both themes) fail the 3:1 floor out of the box; dark-theme focus ring already passes.
- **1.4.12 Text Spacing** — no independent line-height/letter-spacing/word-spacing/paragraph-spacing control for ordinary UI text anywhere in the framework; the underlying tokens are unconsumed dead plumbing.
- **2.5.7 Dragging Movements / 2.5.8 Target Size** — scene item drag has no keyboard alternative; `IconButtonSize::Compact` = 22px < 24px floor.

**Plus baseline 2.0 AA defects that apply regardless of regime:** 1.4.3 Contrast (stock Button, `text_secondary` — confirmed low-effort fix) and 4.1.2 Name/Role/Value (live, systemic AT-staleness bug — confirmed low-effort centralized fix).

**Required conformance artifact:** an **EN 301 549 Accessibility Conformance Report (ACR / ACR-International format)**, covering clause 9 (WCAG 2.1 AA) and clause 11 (11.5 AT interoperability, 11.7 user preferences; 11.8 n/a). This attaches to the shipped **application**, not Bastyde itself — but every app inherits the framework's default-styling gaps unless the app author overrides them, so a framework-level "known gaps" baseline is strongly recommended. Given the re-check's effort findings, EAA-blocking gaps 1–3 in §5 can plausibly be closed in a single short engineering pass ahead of any app-level ACR work.

### 4.2 US Section 508 (Revised, 2017 ICT Refresh)

**In scope:** WCAG **2.0** A+AA (not 2.1 — the 2018 refresh predates 2.1's publication and GSA has not updated the incorporation), plus Chapter 3 (302) Functional Performance Criteria — a technology-neutral outcome test (302.7 limited manipulation, 302.8 limited reach/strength, etc.) that can still catch a 2.1-shaped defect even absent a literal WCAG-2.0 SC number.

**Verdict: Partial, narrower gap surface than EAA/RGAA.** Because 508 incorporates 2.0 only, several surveyed defects are **legally out of scope** as SC violations: 1.4.10 Reflow, 1.4.11 Non-text Contrast, 1.4.12 Text Spacing, 2.5.7 Dragging, 2.5.8 Target Size. What **remains** live and in-scope:

**Blocking gaps unique to this regime's framing:**
- **1.4.3 Contrast (Minimum, 2.0 AA)** — stock Button/Destructive and `text_secondary` still fail; 2.0 has always included this SC. Confirmed low-effort fix (§5a).
- **4.1.2 Name/Role/Value (2.0 A, the most severe conformance tier)** — the live `BindingLevel::Rebuild` AT-staleness bug is squarely in-scope and untouched by the 2.0-vs-2.1 distinction. Confirmed centralized, low-effort fix.
- **Chapter 3 FPC 302.7/302.8** — even though the literal WCAG-2.0 text doesn't name "dragging movements" or "target size," a 508 ACR reviewer applying FPC as a backstop can still flag the scene keyboard-drag gap and the 22px Compact icon button as functional-performance findings.

Note: an earlier draft of this finding also flagged TableView's roving-cell focus as lacking a visual indicator — **this was verified false**: TableView implements a real 4-sided keyboard-focus-visible-gated ring (`table_view.rs:1987-2029`) plus a container fallback ring; this is not a 508 blocker.

**Required conformance artifact:** a **VPAT 2.5 Rev 508**, generating an ACR keyed to WCAG 2.0 A/AA (Chapter 5, §501-503) plus a completed Chapter 3 FPC table. Many federal buyers request the optional WCAG 2.1/2.2 VPAT column in practice even though not legally mandated — procurement reality often exceeds the strict legal minimum, which would re-import the EAA-scoped gaps.

### 4.3 France RGAA 4.1

**In scope:** RGAA 4.1's 106 test criteria derive from WCAG 2.1 AA — the same full criteria set as EAA, not 508's narrower 2.0 set. RGAA's official test methodology is web-authored (DOM/CSS/ARIA-worded techniques) with no officially published native-application equivalent; French public bodies deploying native desktop software bridge to EN 301 549 clause 9+11, so the practical in-scope set mirrors the EAA analysis above, not a literal page-by-page RGAA web audit.

**Verdict: Partial**, same criteria scope as EAA, with one regime-specific amplifying factor:

**Blocking gaps unique to this regime:** RGAA audits are conducted with **real assistive technology** (NVDA/JAWS), which is specifically built to catch the "attribute present but non-functional" pattern this audit found:
- Determinate `ProgressBar` is empirically confirmed to never re-announce its numeric value to AT after its bound `Signal<f32>` changes — its value Prop is registered only at `BindingLevel::RepaintOnly`, never `AccessibilityOnly`, so the fill animates visually while the announced percentage stays frozen at its initial value. (Indeterminate `Spinner`, by contrast, is confirmed correctly wired with `Live::Polite` — this narrows the prior report's framing, which had also implicated Spinner.)
- The `BindingLevel::Rebuild` AT-staleness bug will fail any RGAA test scenario exercising a screen-reader user on a live-updating ListView/TableView/ComboBox — a routine French public-sector UI pattern (dossier lists, démarches).
- The stock theme's contrast failures (Button-on-fill, focus ring, selection tint) directly depress RGAA's **taux de conformité** (a strict per-criterion percentage, not a pass/fail table) on every screen using a Filled/Destructive Button or exhibiting keyboard focus — the single highest-leverage fix given how pervasive these components are, and now confirmed cheap to execute.

**Required conformance artifact:** a **déclaration de conformité** per the official DGNum/RGAA template, citing the **taux global de conformité** as a percentage plus per-theme sub-scores, methodologically bridged via EN 301 549 clause 11 since this is native (not web) software. French law (loi n°2005-102 art. 47, décret 2019-768) requires publication of this declaration **regardless of score** — even "non conforme" must be published, alongside a mandatory **schéma pluriannuel** (multi-year roadmap) and annual **plan d'actions**.

## 5a. Accessible / high-contrast theme strategy for low-vision users

This section resolves an important WCAG nuance raised by the re-check: **the default theme must itself clear AA**, independent of whatever optional high-contrast variant the framework offers. These are two separate, complementary obligations, not alternatives — a dedicated high-contrast theme does not excuse a failing default (WCAG 1.4.3/1.4.11 apply to content "as rendered," and most users never switch themes), while a *dedicated* high-contrast/low-vision variant serves a real, distinct population (EN 301 549 §11.7, users who need well above the AA floor) that a minimally-AA-compliant default is not designed to serve.

### (i) The default theme's minimal AA fix

All of the following are single hardcoded-hex edits in `crates/bastyde-tokens/src/theme.rs`, confined to `ColorTokens::light_default()` (theme.rs:190-300 range) and `ColorTokens::dark_default()` (theme.rs:310-420 range). The resolution chain from token → `TextRole`/`BorderRole` → widget paint is already centralized and correct (`roles.rs:78,80,306`), so no widget code needs to change — every consumer (Button, Checkbox, RadioButton, Slider, Toggle, Avatar, GridView, Splitter, TabBar, SegmentedControl, RadioTile, and more) inherits the fix automatically.

| Token | Theme | Current | Proposed | Paired with | Ratio before → after |
|---|---|---|---|---|---|
| `text_on_accent` | light (theme.rs:216) | `#FFFFFF` | `#000000` | `accent` `#0FB5CC` | 2.47:1 → **8.50:1** |
| `text_on_accent` | dark (theme.rs:341) | `#FDFEFF` | `#000000` | `accent` `#19BDD4` | 2.24:1 → **9.27:1** |
| `text_secondary` | light (theme.rs:214) | `#818594` | `#5F636F` | `surface_content` `#FFFFFF` / `surface_main` `#F7F8FA` | 3.67:1 / 3.46:1 → **6.00:1 / 5.64:1** |
| `text_secondary` | dark (theme.rs:339) | `#6F737A` | `#9198A0` | `surface_content` `#1E1F22` / `surface_main` `#2B2D30` | 3.46:1 / 2.90:1 → **5.65:1 / 4.74:1** |
| `border_focused` / `focus_ring` | light (theme.rs:237,290) | `#0FB5CC` | `#0C8294` (reuses existing `accent_pressed`) | `surface_content` `#FFFFFF` / `surface_main` `#F7F8FA` | 2.47:1 / 2.32:1 → **4.53:1 / 4.26:1** |

`text_on_accent` was chosen over darkening the shared `accent` token deliberately: `accent` also drives focus rings, links, and other consumers, so touching it has a much larger blast radius than necessary, whereas `text_on_accent` has full headroom to go all the way to near-black with no other consequence. Interesting supporting precedent already in the same source file: `ColorTokens::from_os_colors()` (theme.rs:466-469) already implements a luminance-based black/white auto-switch for `text_on_accent` when adopting a live OS accent color — the authors already know this pattern is needed, it was simply never applied to the hardcoded stock presets (and the luminance threshold used there, `> 0.4`, is itself slightly too permissive against the true ~0.18 crossover for 4.5:1 — a secondary observation worth fixing in the same pass).

`surface_selected` (the row/menu/tab selection wash) is the one sub-item that does **not** reduce to a hex tweak: reaching 3:1 as a flat pale wash requires abandoning the "subtle tint" aesthetic entirely. The recommended path is to keep the wash and add a thin (1–2px) accent-colored leading-edge indicator that independently carries the required 3:1 boundary — this is real, if small, feature work (touches `recipe_standard_item_style.rs` and `menu_list.rs`'s `KeyboardHighlightWrapper`), tracked separately so it doesn't block shipping the four trivial-tweak fixes above.

Action items: apply the six hex edits above; strengthen `theme.rs:707-711`'s `assert_ne!`-only test into a real `>= 4.5` (text) / `>= 3.0` (non-text) ratio assertion for both presets; add the missing `contrast_ratio()` helper to `color.rs` (currently only `relative_luminance()` exists) so this and future preset validation share one implementation; scope `surface_selected` as its own follow-up ticket.

### (ii) A dedicated high-contrast / low-vision theme variant

Independent of (i), the framework should build on its **already-shipped but unconsumed** `prefers_high_contrast` signal to serve users who need well beyond bare AA — the EN 301 549 §11.7 "respect user preferences" clause, and the population the "Increase Contrast" OS setting exists for.

**What's already there:**
- `PaintContext::prefers_high_contrast: bool` (`crates/bastyde-core/src/widget/paint_context.rs:48-49`) is threaded into every `PaintContext` construction on every paint pass (`crates/bastyde-core/src/widget_tree/rendering_impl.rs:135,425,563,604`), sourced from the OS via `AccessibilityPreferences::query()` (`crates/bastyde-app/src/window_manager.rs:213`).
- `WidgetTree::set_accessibility_preferences` (`crates/bastyde-core/src/widget_tree.rs:1871-1899`) already implements correct diff + `mark_all_dirty` + `recompute_effective_theme` semantics for a runtime preference change — it just has no post-startup caller today (the OS query runs exactly once, at `WindowManager::new`).
- A directly analogous precedent already exists in the same file: `ColorTokens::for_inactive_window()` (`theme.rs:177-189`) swaps a subset of tokens (the accent family + focus indicators) via a pure `ColorTokens -> ColorTokens` transform, applied by the paint walker exactly the way a high-contrast variant would need to be.

**Wiring steps (small, well-precedented, not greenfield):**
1. Add `ColorTokens::for_high_contrast(&self) -> ColorTokens` to `crates/bastyde-tokens/src/theme.rs`, sibling to `for_inactive_window`, targeting headroom well past bare AA (e.g. ≥7:1 for text, ≥4.5:1 for non-text UI components — the WCAG AAA / EN 301 549 §11.7 aspirational tier, appropriate for an opt-in high-contrast mode).
2. Wire it into the paint walker the same way `for_inactive_window` is already wired in `rendering_impl.rs`: when `tree.prefers_high_contrast` is true, swap `effective_theme.colors` for the high-contrast variant, reusing the existing `recompute_effective_theme`/`mark_all_dirty` plumbing already built for the text-scale and window-active features (`widget_tree.rs:1479`).
3. Add the missing live re-poll (§5, `prefers_high_contrast` gap row) so a mid-session OS toggle ("Increase Contrast") takes effect without an app restart — the diff/dirty-mark machinery already handles this correctly once a caller exists.

**Which token families to override**, in priority order (all already resolvable per-theme without new plumbing beyond the swap function above):
- **`accent` / `text_on_accent`** — push the accent hue and its paired text color to their most separated extremes (this is the same pair fixed for the *default* theme in (i), but a high-contrast variant can go further than the minimal-AA fix, e.g. pure black-on-saturated-accent or accent-on-pure-white).
- **`focus_ring` / `border_focused`** — the single highest-value override for keyboard/low-vision users; widen well past 3:1 (the default-theme fix in (i) targets ~4.5:1; a high-contrast variant can push toward a bolder, higher-contrast, possibly thicker ring — `recipe_button_style.rs:259-262` already parameterizes stroke width alongside color).
- **`surface_selected`** — exactly the token identified in (i) as unable to reach 3:1 as a flat wash in the default theme; a high-contrast variant is the natural home for a stronger, fully-compliant selection fill (or the accent-edge-indicator approach) without touching the default aesthetic at all.
- **`text_secondary`** — push further than the default-theme minimal fix; a high-contrast mode is exactly where "subtle" secondary text should stop being subtle.

**Why (i) and (ii) are complementary, not alternatives:** WCAG 1.4.3/1.4.11 are unconditional — they bind on whatever theme actually renders by default, for every user, not just those who know to opt into a high-contrast mode (most users never change the default). Shipping only (ii) without (i) would leave the shipped default itself in violation, and — per EN 301 549's ACR model — an app cannot claim baseline conformance by pointing to an optional variant the default UI doesn't surface or default to. Conversely, shipping only (i) without (ii) satisfies the *floor* but ignores the explicit EN 301 549 §11.7 obligation to honor an OS-level "prefers more contrast" signal, and underserves genuinely low-vision users for whom 4.5:1 is usable but not comfortable. The two tracks touch almost entirely disjoint code (a handful of hex constants vs. a new `ColorTokens` transform function + wiring + a live-repoll listener) and can ship independently, in either order, with (i) recommended first given its `minutes` effort and blocker severity.

## 6. Strengths

- **A real, unconditional AT bridge on every window, on all three desktop OSes.** `PlatformWindow::new_with_a11y` (`window.rs:122-128`) is called for every live window with no feature gate (`window_manager.rs:587`), and the resulting `TreeUpdate` is pushed every redraw frame (`app.rs:1621-1622`) into a genuine `accesskit_winit::Adapter`. This is the make-or-break foundation for all three regimes, and it is genuinely present — not a stub, not opt-in.
- **Broad, mostly-correct static Role/Name/Value coverage.** Every interactive widget surveyed (25+ families: Button, Checkbox, RadioButton, Toggle, Slider, ComboBox, SpinBox, TextInput, TabBar, MenuItem, ListView/TreeView rows, TableView, TreeTableView, ProgressBar, Dialog, Popover, Snackbar/Toast/Banner, and more) sets a distinct, semantically-correct AccessKit Role plus a real Name and relevant State/Value.
- **Genuine AT write-back.** AT-invoked actions (SetValue, ReplaceSelectedText, Increment/Decrement, SetTextSelection) route through a real channel into actual widget/document state mutation (`window.rs:452-455` → `event_dispatch_impl.rs:1186-1274`), confirmed for 15+ widgets, not a token gesture.
- **Real table/grid semantics.** TableView and TreeTableView emit complete `Table`/`TreeGrid` structure with row/column counts and per-cell indices (`table_view.rs:2073-2079`, `a11y.rs:98-253`) — a genuinely conformant implementation of one of the hardest AT patterns to get right.
- **A well-designed tooltip content architecture** (for the Rich/Composite tiers) that correctly implements all three sub-requirements of WCAG 1.4.13 (dismissible, hoverable, persistent) via dwell-to-sticky promotion, a `Role::Dialog` flip, and an advertised `Focus` action rather than stealing focus.
- **A mostly-correct, well-tested reduced-motion story.** `ctx.prefers_reduced_motion()` / `to_or_snap()` is honored across nearly every animated wrapper widget (Collapse, Fade, Pulse, Cycle, Slide, Shake, Scale, Crossfade, SmoothSize, Spinner, ProgressBar::indeterminate), and the re-check confirms `Blur` — initially suspected of the same gap — is correctly designed to delegate motion responsibility to its caller with zero misuse in the codebase today.
- **A dangling-relationship and duplicate-child defense layer** that actively prevents malformed AT trees rather than merely hoping app authors get it right (`accessibility_impl.rs:243-340`, `assert_no_dangling_relationships`).
- **A real, tested locale/language pipeline** (`3.1.1`) — BCP-47 tags on the AT root, reactive to runtime locale switches, with a dedicated regression test.
- **Well-precedented internal patterns that make the highest-priority fixes cheap.** The re-check found that nearly every Blocker/High-severity gap has a near-identical, already-shipped sibling pattern elsewhere in the codebase to copy: `for_inactive_window()` for the proposed `for_high_contrast()`; the dormant/active `a11y_dirty` set for the proposed `Rebuild` fix; Button/Avatar/Calendar/DateEdit's `AccessibilityOnly` registration for the proposed ProgressBar fix; `hidden`'s `register_if_bound` call for the proposed label/value/description fix. This lowers the real-world risk and cost of the roadmap below considerably.

## 7. Recommendations & Roadmap

### Quick wins (minutes-to-hours; re-checked effort estimates)

1. **Fix the `BindingLevel::Rebuild` AT-staleness bug** — one line in `process_pending_rebuilds` (`layout_impl.rs`), **minutes**. The single highest-leverage fix in this audit; centralized and retroactively covers ~25 widget files / 92 call sites.
2. **Apply the six default-theme hex edits in §5a** (`text_on_accent` ×2, `text_secondary` ×2, light `border_focused`/`focus_ring` ×2) — **minutes**. Clears the Button-contrast and light-focus-ring Blocker findings with margin; zero widget code changes.
3. **Register the determinate `ProgressBar` value at `BindingLevel::AccessibilityOnly`** — **minutes**, one line, the same idiom used 6+ places already.
4. **Register `access_label`/`access_value`/`access_description` for `AccessibilityOnly` reactivity**, mirroring the existing `access_hidden` registration, and extend `arena.rs::apply_handler_set`'s post-mount path — **minutes**.
5. **Route `Popover`'s internal overlay-fade fast path through `prefers_reduced_motion`** — **minutes**, a same-object method call away. (`Blur` needs no change — confirmed not defective.)
6. **Wire `access_described_by`** from each of the 5 `ValidationStrip` consumers (TextInput, PasswordField, DateEdit, DateTimeEdit, DateRangeEdit) to their field — **hours**, mechanically identical per file.
7. **Auto-wire `access_labelled_by`** inside `FormLayout::line()`/`line_ids()` — **hours**.
8. **Fix DateEdit's duplicate AT node** by building `TextInputField` directly instead of routing through `TextInput` (following the `SpinBox` precedent) — **hours**.
9. **Forward text-run formatting (bold/italic/weight/underline/strikethrough) to AccessKit** in `push_text_run_child` — **hours**, 3 call sites total.
10. **Add a keyboard-nudge mode to `SceneView`** for selected-item repositioning, and close the `IconButtonSize::Compact` target-size gap (hit-slop padding, design-preserving) — **hours**.
11. **Wire `prefers_high_contrast` into a real `ColorTokens::for_high_contrast()`** (§5a part ii) plus a live OS-preference re-poll listener — **hours**, directly mirrors `for_inactive_window`.

### Larger efforts (days, or blocked in part on external factors)

15. **Design and ship a real `surface_selected` fix** (§5a) — either a genuinely non-wash mid-tone fill or, recommended, a secondary accent-colored edge indicator paired with the existing wash — **hours to days**, needs design sign-off, scoped separately from the trivial focus-ring fix it was originally bundled with.
16. **Design and ship a Text Spacing control surface** (independent line-height/letter-spacing/word-spacing scale multipliers on `TypographyTokens`, plumbed all the way through to the text-typeset shaping layer, which does not consume these tokens today) exposed through a settings-bound control parallel to `TextScaleControl` — **days**, cross-crate.
17. **Design a full Identify Input Purpose taxonomy** for `TextInputField` (WCAG 1.3.5) beyond the documented partial-credit escape hatch — genuine OS-autofill conformance requires an **upstream AccessKit contribution**, since 0.24.1 has no autocomplete-token field; track as an external dependency, not a pure Bastyde task.
18. **Publish a framework-level "known accessibility gaps" addendum** app authors can cite directly in their own ACR/VPAT/déclaration de conformité methodology sections, since these framework-default defects are not discoverable without an audit of this depth.

Taken together, items 1–5 alone — all now confirmed as **minutes**-scale, single-function fixes — would resolve every Blocker-severity finding in this audit (the AT-staleness bug and the default-theme contrast failures) plus one High-severity finding (ProgressBar narration). They should ship ahead of everything else. Items 6–14, all **hours**-scale and well-precedented against existing codebase patterns, close out the remaining High/Medium findings and can reasonably land in the same short engineering cycle. Only items 15–17 involve genuine design decisions, cross-crate plumbing, or an external upstream dependency, and should be tracked on a longer roadmap — with item 15 (`surface_selected`) recommended as the first of these three to schedule, since it is the last unresolved contrast-Blocker component.
